### 17. No `ILayer` / Module Registry for Composing Novel Architectures

All architecture variants (`DecoderArch`, `TransformerBlock`, attention types, FFN types) are concrete classes. There's no lightweight `ILayer` abstraction that would let a researcher compose a custom architecture from a config string or YAML without writing C# class definitions.

A minimal module registry pattern:

```csharp
// Register a custom FFN variant
LayerRegistry.Register("MoE-FFN", cfg => new MoEFeedForward(cfg));

// Compose from config
var block = LayerRegistry.Build(config.FfnKind, config);
```

The existing `FfnKind`, `AttentionKind`, `NormKind` enums are already doing this conceptually — the gap is that adding a new variant currently requires adding an enum case, a class, and a switch branch, rather than just registering a factory.


## Part 5: Architectural Suggestions for Experimentation

These don't affect performance directly but make the codebase genuinely better as an experimental platform:

**Separate `IForwardPass` from `ITrainable`** — currently `Transformer` owns both inference-time logic and training-time parameter management. Splitting them makes it trivial to wrap a model in a distillation harness or a LoRA adapter without touching `Transformer` itself.

**Make `Workspace` scope-aware** — a simple stack of offsets would allow nested allocations (useful when an experimental module wants its own scratch space without interfering with the outer workspace). The bump allocator is already there; add `Push()` / `Pop()` scope markers.

**Typed experiment config** — a base `ExperimentConfig : SharpMindConfig` class that carries metadata (name, description, hypothesis) alongside model hyperparameters. Trivial to add, makes checkpoint logs and experiment tracking far easier.

**`IScheduler` chaining** — the existing schedulers (cosine, warmup, linear) are good but not composable. A `ComposedScheduler` that chains stages (warmup → cosine → constant tail) would cover most real training runs without writing a custom scheduler.

Critical Review
1. Agent-as-Tool Sub-agents (IAgentBuilder.CreateAgent)
Good idea, but high complexity for the actual benefit:

What it requires: Each sub-agent needs its own generator context (model instance + KV cache). Sharing a single generator across agents means serializing generation requests — no parallelism. Creating separate model instances means 2×–10× memory.
The lightweight alternative: Sub-agents that reuse the parent's generator as a pure "prompt → response" call with a fresh mini-context (system prompt + single user message + stop condition). No persistent KV cache, no session history. This is basically generator.GenerateFromTokensAsync() with a custom system prompt. Much cheaper.
Depth control: Absolute must. Configurable max depth (default 3–5). Pass currentDepth through the call chain, reject at limit.
Naming: Greek names as a default convention is fine but shouldn't be enforced. Let the user optionally name their agents. Auto-name with Greek letters if not provided (Alpha, Beta, Gamma...).
My recommendation: Implement as a lightweight delegate pattern first — CreateAgent(name, systemPrompt) returns a Func<string, Task<string>> that calls the shared generator. No full ChatSession per agent. This gets 90% of the value at 10% of the cost.
2. Post-processors / Context Window Reduction
The current truncation (tail-drop when promptToks.Length > MaxTokens) is dangerously naive — it can silently drop the system prompt + agent instructions.

Better strategies, ordered from simplest to most sophisticated:

Strategy	Effort	Impact	Risk
Priority truncation — keep system prompt + tool results + most recent user/agent turns, drop middle history	Low	High	Low
Importance metadata — tag messages with IsPinned / importance score, evict lowest-scored first	Low	Medium	Low
Sliding window — keep last N messages/tokens, full stop	Low	Medium	Low
History summarization — use LLM to condense old turns into a summary message	High	Very High	High (cost, quality)
My recommendation: Start with priority truncation (smarter than tail-drop, no LLM calls). Add IsPinned metadata. Defer summarization.

3. ChatSession States + History Context Tagging
States: ChatStatus already has Thinking, Updating, Executing, Responding, Waiting, Interrupted, Complete. But:

Updating is never emitted — should fire during context management
Waiting is never emitted — should fire when waiting for tool results or user input
Wiring these up is nearly zero-effort and makes the API honest.
History metadata: Adding a Dictionary<string, string>? Metadata or Tags field to ChatMessage is trivial. The hard part is populating it meaningfully:

Auto-tagging via the model is expensive and unreliable
Manual tagging via API (ChatMessage.WithTag("code_review", "session-3")) is simple but requires user buy-in
Recommendation: Add the field, populate it manually via API surface. Don't auto-tag until there's a concrete use case demanding it.
4. Interrupt & Recovery
True recovery (serialize KV cache, resume mid-token) is a moonshot — the KV cache is megabytes of opaque float buffers, architecture-specific, not serializable in the current design.

Soft recovery (pragmatic and implementable):

On interrupt, save the partial response to _history as an Agent message with an Interrupted: true metadata flag
On resume, inject a system message: "The previous response was interrupted. Continue from where you left off."
No KV cache serialization needed
The model re-generates from scratch but has the context of what was happening
Cost: Re-generating the full response instead of resuming mid-stream
My recommendation: Implement soft recovery. It's maybe 20 lines of code and dramatically improves UX over "start completely over."
