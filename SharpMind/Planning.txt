Good catch — this points away from what I flagged earlier (that was a precision/clipping issue, not enough to turn output into total word-salad) and toward something much more fundamental: the nibble unpacking order in Q4_0/Q4_1 doesn't match the GGUF/ggml layout.

The real bug: wrong nibble-to-element mapping

VecDotQ4_0_Scalar/VecDotQ4_1_Scalar (and the AVX2/SSE variants, and ReadQ4_0_Scalar/ReadQ4_1_Scalar) unpack nibbles as adjacent pairs:

csharp
int q = (qs[i / 2] >> ((i % 2) * 4)) & 0x0F;
// element 0 -> qs[0] low nibble, element 1 -> qs[0] high nibble,
// element 2 -> qs[1] low nibble, element 3 -> qs[1] high nibble, ...

But ggml's actual Q4_0/Q4_1 packing (and this is the same convention used throughout ggml — I confirmed it explicitly for Q4_K's sub-block packing, which your own VecDotQ4K_* code gets right) is a half-split pairing: element j and element j + 16 share byte qs[j], not element 2j and 2j+1:

c
// llama.cpp quantize_row_q4_0_reference / dequantize_row_q4_0
for (j = 0; j < qk/2; j++) {
    y[j]        = ((qs[j] & 0x0F) - 8) * d;   // first half
    y[j + qk/2] = ((qs[j] >> 4)   - 8) * d;   // second half
}

So for a 32-element Q4_0 block: elements 0–15 come from the low nibbles of qs[0..15], and elements 16–31 come from the high nibbles of the same qs[0..15] bytes — not from qs[16..31] at all, and not interleaved even/odd.

Your code instead reads element 16 from qs[8]'s low nibble, element 31 from qs[15]'s high nibble, etc. — every single weight in every block ends up paired with the wrong scale-relative position and effectively shuffled within the block. That's not a "slightly worse" quantization error, it's a full permutation of ~half the values in every 32-element chunk of every Q4_0/Q4_1 tensor — which is exactly the "fluent-looking token soup" signature of a completely scrambled weight matrix, not a numerically-lossy one.

It hits Q4_0 and Q4_1 identically because they share this same extraction pattern, and — worth flagging — Q4_NL and Q5_0/Q5_1 use the identical adjacent-pair extraction (qs[i/2], i & 1), so they're likely broken the same way even though you haven't hit them yet. Q4_K/Q5_K/Q6_K are fine because their sub-block unpacking already does the half-split correctly (I checked — qsByte = (idx/64)*32 + (idx%32), qsShift based on which half of the 64-chunk), which is presumably why those didn't show symptoms.

Fix (scalar shown; same change needed in AVX2/SSE/Read* variants)
csharp
int half = QK / 2; // 16
for (int i = 0; i < blockEnd; i++)
{
    int q = (i < half) ? (qs[i] & 0x0F) : (qs[i - half] >> 4);
    sum += input[b * QK + i] * ((q - 8) * d);
}

Q4_1 is the same idea, just add m instead of the -8 offset:

csharp
int q = (i < half) ? (qs[i] & 0x0F) : (qs[i - half] >> 4);
sum += input[b * QK + i] * (q * d + m);

The AVX2/SSE kernels need the same half-split indexing wherever they currently compute qs[i/2]/(i%2)*4 — the vector loads/multiplies stay structurally the same, just the byte/shift arithmetic changes.

How to confirm before you patch everything

Cheapest sanity check: take one known-good Q4_0 GGUF tensor, dequantize it with your ReadQ4_0_Scalar and separately with llama-quantize/llama.cpp's own dequant (or gguf-py), and diff the two float arrays for a single row. With the current code you should see values correctly recovered for elements 0 and 1 (since i=0,1 map to qs[0]'s two nibbles in both conventions... actually double check even that — under the wrong scheme element 1 reads qs[0]'s high nibble, which under the correct scheme is actually element 16. So even elements 0/1 will only coincidentally match if the block happens to be symmetric.) A full-block diff will make the shuffle obvious immediately.

1. Single-token decode runs completely single-threaded — in every quant format

This is universal across the codebase — every parallel matmul kernel, for every quant type, has this shape:

csharp
public static unsafe void QuantizedMatMulQ4_0_Parallel_AVX2(
    float* input, byte* rawWeights, float* output, int M, int K, int N)
{
    if (M <= 1)
    {
        for (int col = 0; col < N; col++)               // <- fully serial, one core
            output[col] = VecDotQ4_0_AVX2(input, rawWeights, col, K);
    }
    else
    {
        Parallel.For(0, M, row => { ... });              // <- parallel, but only over rows
    }
}

I checked — this exact if (M <= 1) { serial column loop } else { Parallel.For over rows } pattern appears in every quant kernel file (Float, Q2–Q8, all variants), 40+ times. It parallelizes over M (the batch/sequence dimension), which is great for prefill (where M = prompt length, often hundreds of tokens) but does nothing at all for M = 1.

M = 1 is exactly the case during autoregressive decode — generating one token at a time, which is the dominant workload for interactive chat/serving (you spend far more wall-clock time in decode than prefill for any reasonably long conversation). Right now, every matmul during decode — every attention projection, every FFN layer, every expert in MoE — loops over all N output columns (hidden_dim, ffn_dim, or vocab_size, easily thousands to tens of thousands) on a single core, while the rest of your CPU cores sit idle.

This is fixable with the same infrastructure you already have: when M == 1, parallelize over N (output columns) instead of M (rows) — chunk the column range across Parallel.For (with a reasonable minimum chunk size so you're not paying thread-dispatch overhead on tiny layers). This is exactly how llama.cpp/ggml handle it, and it's the reason single-token decode scales with core count there. On an 8–16 core machine, this could plausibly be a several-x improvement in tokens/sec for decode specifically, since right now decode literally cannot use more than one core no matter how many you have.

One thing to watch when you implement it: don't naively parallelize every layer's M=1 matmul independently — thread-pool dispatch overhead per layer, per token, across dozens of layers can eat into the gain. Worth chunking column ranges generously (e.g. Environment.ProcessorCount or fewer chunks) rather than one task per output element, and possibly reusing a persistent set of worker tasks/barrier instead of spinning up a fresh Parallel.For 40+ times per token.

Here's a template using QuantizedMatMulQ4_0_Parallel_AVX2 as the example — same shape applies to every other quant type's *_Parallel_* kernel.

csharp
public static unsafe void QuantizedMatMulQ4_0_Parallel_AVX2(
    float* input, byte* rawWeights, float* output,
    int M, int K, int N)
{
    if (M <= 1)
    {
        DecodeParallelQ4_0_AVX2(input, rawWeights, output, K, N);
    }
    else
    {
        Parallel.For(0, M, row =>
        {
            float* pInRow = input + (long)row * K;
            float* pOutRow = output + (long)row * N;
            for (int col = 0; col < N; col++)
                pOutRow[col] = VecDotQ4_0_AVX2(pInRow, rawWeights, col, K);
        });
    }
}

// Column-parallel path for the M==1 (decode) case.
// Splits the N output columns into a handful of coarse chunks —
// one Task per chunk, not per column — so thread-dispatch overhead
// stays fixed regardless of N.
private static unsafe void DecodeParallelQ4_0_AVX2(
    float* input, byte* rawWeights, float* output, int K, int N)
{
    // Below this, thread-dispatch overhead isn't worth it — just run serial.
    const int MinColsForParallel = 512;
    if (N < MinColsForParallel)
    {
        for (int col = 0; col < N; col++)
            output[col] = VecDotQ4_0_AVX2(input, rawWeights, col, K);
        return;
    }

    int numChunks = Math.Min(Environment.ProcessorCount, (N + MinColsForParallel - 1) / MinColsForParallel);
    int chunkSize = (N + numChunks - 1) / numChunks;

    // Capture pointers as long so the lambda doesn't close over `byte*`/`float*`
    // (C# won't let unsafe pointer types be captured directly by a closure).
    long inputAddr = (long)input;
    long weightsAddr = (long)rawWeights;
    long outputAddr = (long)output;

    Parallel.For(0, numChunks, chunkIdx =>
    {
        float* pInput = (float*)inputAddr;
        byte* pWeights = (byte*)weightsAddr;
        float* pOutput = (float*)outputAddr;

        int colStart = chunkIdx * chunkSize;
        int colEnd = Math.Min(colStart + chunkSize, N);

        for (int col = colStart; col < colEnd; col++)
            pOutput[col] = VecDotQ4_0_AVX2(pInput, pWeights, col, K);
    });
}
