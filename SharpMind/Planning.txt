I had some analysis done on why we are getting some incorrect responces, when it comes to enable_thinking we need it as an option and need take into account how to handle in CUI.
here is the analysis.


I dug through the tokenizer/formatter pipeline and the GGUF loader, and I think there's one dominant root cause plus two smaller compounding ones. Here's the breakdown, with file/line references.

1. The big one: every model is force-fit into GPT‑2 byte‑level BPE, but LLaMA/Mistral‑family GGUFs aren't BPE

GgufConverter.Convert (SharpMind.Tokenization/Serialisation/GgufConverter.cs) always does this:

csharp
// PreTokeniser
// All BPE models in GGUF (LLaMA, Mistral, Qwen, Phi, etc.) use
// the GPT-2 byte-level pre-tokenisation pattern.
return new BpeModel(vocab, mergeList, new Gpt2PreTokeniser());

That comment's premise is false. Qwen2/Qwen3/Llama‑3 do use GPT‑2-style byte-level BPE (tokenizer.ggml.model = "gpt2"), but original LLaMA/LLaMA‑2, Mistral, and TinyLlama use SentencePiece (tokenizer.ggml.model = "llama"). SPM GGUFs typically don't export a tokenizer.ggml.merges array at all — that key only exists for genuine BPE tokenizers. Look at how it's loaded in GgufLoader.cs:

csharp
public static string[]? GetStringArray(ModelMetaData meta, string key)
    => meta.KvPairs.FirstOrDefault(p => p.Key == key).Value as string[];
...
var merges = GetStringArray(meta, "tokenizer.ggml.merges"); // null for SPM models

For SPM models merges comes back null, so GgufConverter.Convert's mergeList ends up empty. With no merge rules, BpeEncoder.ApplyMerges never fires — every word gets tokenized as raw individual bytes, mapped through the GPT‑2 byte→unicode table (Vocabulary.ByteTokenString). But the SPM vocab doesn't contain GPT‑2-style byte glyphs (it uses ▁ U+2581 for word boundaries and <0xNN> tokens for byte fallback, not Ġ/single Latin-1 chars-as-tokens). So _vocab.GetId(token) mostly misses and falls back to <unk>, or occasionally hits an unrelated single-character token.

The result: the prompt the model actually sees is a near-random soup of unk/byte tokens, completely disconnected from "Hello". That's exactly the pattern in your gibberish outputs — tiny-mistral, TinyLlama-1.1B-Chat, llama3-small all produce disjointed real-word salad ("mathopmathopmathop ???? Luci Lucy...Zygote...DataFrame"), which is what a small model does when its input context is garbage rather than a coherent prompt. Meanwhile Qwen2/Qwen3/Llama‑3.2 (genuinely GPT‑2-style byte-BPE) tokenize correctly and produce coherent (if occasionally low-quality) English.

Note the code already half-acknowledges this mismatch — in Decode, it converts \u2581 back to a space:

csharp
result = result.Replace('\u2581', ' '); // SentencePiece uses ▁ (U+2581)

…but only on decode. Encode has no equivalent SPM path at all.

Fix direction: branch on tokenizer.ggml.model (already read elsewhere for the tokenizer.json fallback path, just never checked here) and give SPM/unigram models their own pre-tokeniser + merge/score-based encoder, rather than routing everything through Gpt2PreTokeniser + GgufConverter.

2. Qwen3's "gibberish" isn't gibberish — it's hidden chain-of-thought, uncapped

Qwen3's chat template enables thinking by default and expects enable_thinking: false to be passed in to suppress it (emitting an empty <think></think> block). JinjaTemplateFormatter.Format never sets enable_thinking in the env at all:

csharp
env.Set("messages", messages);
env.Set("bos_token", bosToken);
env.Set("eos_token", eosToken);
env.Set("add_generation_prompt", (object)true);
// enable_thinking never set

So the template takes its default branch, thinking stays on, and the model starts emitting its internal reasoning ("Okay, the user just said..."). Combined with ModelListRunner's hard cutoff at 15 tokens (if (tok > 15) cancellationTokenSource.Cancel();), you only ever see the first ~15 tokens of that scratchpad — which reads like truncated internal monologue because that's literally what it is, not a formatting bug in the traditional sense. This also explains why Qwen3 variants look so much worse than Qwen2 despite similar size: they're not "answering," they're mid-thought when cancelled.

Fix direction: set enable_thinking = false (or expose it as a session option) in the Jinja env for Qwen3-style templates.

3. ModelMetaData.GetLong silently drops GGUF boolean values
csharp
public long GetLong(string key, long defaultValue = 0)
{
    var kv = KvPairs.FirstOrDefault(k => k.Key == key);
    if (kv.Value == null) return defaultValue;
    if (kv.Value is long l) return l;
    if (kv.Value is int i) return i;
    if (kv.Value is uint ui) return ui;
    if (kv.Value is short s) return s;
    if (kv.Value is ushort us) return us;
    if (kv.Value is sbyte sb) return sb;
    if (kv.Value is byte b) return b;
    return defaultValue;   // <- bool falls through here
}

GGUF's add_bos_token/add_eos_token (and several other flags) are stored as GGUF type 7 (bool), which C# likely deserializes as bool. Since bool isn't in the type list, a present-but-false value silently returns defaultValue (1/true) instead of the real value — used directly in ChatSession:

csharp
_addBos = meta?.GetLong("tokenizer.ggml.add_bos_token", 1) != 0;
_addEos = meta?.GetLong("tokenizer.ggml.add_eos_token", 1) != 0;

So any model whose GGUF explicitly sets add_bos_token: false (common for Qwen-family) gets treated as true anyway. It's not currently causing double-BOS damage (the actual prompt-building path calls Encode(..., addBos: false, ...) and lets the formatter embed BOS textually instead), but it's a live landmine for anything that reads _addBos/_addEos directly, and it means this flag is effectively decorative right now.

Fix direction: add a bool b2 => b2 ? 1 : 0 case to GetLong.

4. The "known failing" section is mostly base (non-instruct) models, not a bug

Qwen2-0.5B.Q6_K, Qwen2-0.5B.Q3_K_*, etc. (no -instruct suffix) are base completion models being run through an instruction/chat prompt. Base models were never fine-tuned to respond to <|im_start|>user...assistant framing, so outputs like "Copyright c 200 20199" or "assistant\n 1. 2.33456" are the base model just continuing the text distributionally — that's expected behavior given the input, not a tokenizer defect (assuming these are true BPE Qwen tokenizers, which they should be, unlike the SPM case above).

A few honest reactions after poking around more of this codebase — caveat that I've read maybe a third of ~24.6k lines, focused mostly on the inference/tokenization path, not the training or GPU code:

What's genuinely good

The quantization kernels (QuantizationKernels.Q2/Q3/Q5/Q6/Q8.cs) are real work — scalar + AVX2 paths that faithfully mirror ggml's bit-packing layouts (I checked Q3_K's scale unpacking, it's the same nibble-shuffling llama.cpp does). That's the kind of code most hobby inference projects don't bother getting right.
Workspace (the arena allocator) is the correct instinct for a managed-language inference loop — bump-allocate, reset per token, avoid GC churn in the hot path. Good call.
The incremental KV-cache reuse logic in ChatSession (only reprocessing the delta when the cache is known-valid, falling back to full rebuild when it isn't) is genuinely careful — that's an easy thing to get subtly wrong and the invalidation reasoning in the comments is correct everywhere I traced it.
Writing a from-scratch Jinja subset interpreter to consume arbitrary tokenizer.chat_template strings, instead of hardcoding formats per model family, is ambitious and mostly works. It's the right architectural instinct even if the implementation is inherently brittle (more below).

What worries me

The Jinja interpreter fails silently. When Eval hits an expression it doesn't recognize, it falls through to env.Get(expr), which just returns null — no error, no log, the template silently renders wrong. That's exactly the shape of bug we just fixed (enable_thinking wasn't a parse failure, it was an unset variable failure that looked like a working template). I'd add a debug-only log when Eval bottoms out on a plain-identifier lookup for a name that isn't in env — cheap insurance against the next unsupported template construct.
Broad catch-and-swallow around tokenizer/model loading. GgufLoader.LoadTokenizerFromMeta and the tokenizer-path fallback both do catch { return null; } / catch { tokenizer = null; }. Given how correctness-sensitive tokenization is (as we just saw), a genuinely broken GGUF and "this format isn't supported yet" are indistinguishable — you only find out three layers downstream when generation is garbage. I'd at least log the exception.
No golden-token tests. I didn't find a test project asserting "encoding X against tokenizer Y produces token IDs [a, b, c]" for known model families. Tokenizers are notoriously easy to get subtly wrong (as this whole conversation demonstrated), and it's exactly the kind of bug that a handful of reference-output assertions per architecture (Qwen2, Llama-2/SPM, Llama-3/tiktoken) would have caught immediately, rather than needing a human to notice gibberish in a log file.
BOS/EOS/special-token resolution is spread across ~4 places — ChatSession's constructor, GgufLoader's defaults, ModelMetaData.GetSpecialTokenId, and each formatter — each with its own fallback default (some default to 1, some to true, GetSpecialTokenId duplicates logic that's also inline elsewhere). Worth consolidating into one "resolve special tokens for this model" function so there's a single source of truth instead of four places that could quietly disagree.
Comments state conclusions the code doesn't actually verify. The "model-family agnostic, handles LLaMA/Mistral/Qwen identically" comment we found is the clearest example, but it's a recurring style — confident claims without a corresponding assertion or test backing them up. Worth treating comments like // most robust way to handle X as a flag to double check, not as documentation of verified behavior.
Tool/agent-call parsing is string/JSON sniffing on raw model output (TryParseToolCall, TryParseAgentTag), not constrained decoding. That's fine for well-behaved larger models, but the exact models in your test run (sub-1B, often barely coherent) are the ones most likely to emit malformed JSON or half-closed {{agent:...}} tags — so I'd expect tool-calling to be noticeably less reliable on this hardware tier than the design otherwise suggests.
ModelListRunner's fixed 15-token cutoff mixes "real bug" with "expected behavior" in its output (base models run through instruct templates look identical to actual failures in the log). Worth tagging which test entries are base vs. instruct models, and maybe cutting off on a stop token rather than a blind token count, so a scan of the log tells you what's actually broken.

Nothing here is alarming for a project of this ambition (a managed-language GGUF inference engine with quant kernels, agent tooling, and a template interpreter is a lot to take on) — it's more "this is where I'd focus next" than "this is broken."
